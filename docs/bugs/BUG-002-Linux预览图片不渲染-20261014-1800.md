## 一句话概述

Linux 上打开含本地图片的 Markdown 文档，图片路径正确、语法正确、图片文件存在，但预览区图片不渲染，也无任何错误提示。

## 复现步骤

1. Linux 上安装 0.3.0 deb 版并打开应用（报告人的书库状态见 BUG-001：侧栏为上次恢复的旧目录）；
2. 打开一篇含本地图片引用的 .md 文档；
3. 观察预览区图片。

## 预期行为

- 本地图片正常显示；
- 若图片无法加载，应有可见的失败占位与原因提示（路径不存在 / 不在书库内 / 无权限），而不是静默空白。

## 实际行为

- 图片位置空白，无任何报错信息，无法区分"路径错了 / 权限拒了 / 渲染器 bug"。

## 图片加载管线（代码事实，供定位）

1. **渲染端改写 src**（`src/renderer/src/preview.ts:165-180`）：非 `http(s)`/`data:` 的图片 src，先 `decodeURIComponent`（去掉 `?`/`#` 后缀），然后**无条件拼接在当前文档所在目录之后**（`abs = baseDir + '/' + clean`），再编码为 `mdasset://local/<绝对路径>`；
2. **主进程 mdasset 协议**（`src/main/index.ts:112-126`）：解码、`path.normalize` 后，检查路径必须以**当前书库根目录**开头（`abs.startsWith(root + path.sep)`），否则返回 **403**；文件读取失败返回 **404**；MIME 按扩展名小写匹配（`src/main/index.ts:19-27`）；
3. **CSP** 已放行 `mdasset:`（`src/renderer/index.html:5`），排除；
4. **应用内插入图片**会先复制到 `<文档目录>/assets/img-<时间戳>.<扩展名>` 并写入相对路径（`src/main/ipc.ts:256-267`、`src/renderer/src/main.ts:379-391`），该链路本身正常。

## 候选根因（按可能性排序，待报告人补充信息裁决）

### 候选 1：图片不在当前书库根目录内 → 协议层 403（结构性最可疑）

mdasset 协议**只允许加载当前书库根目录之内的图片**（`src/main/index.ts:116`）。两种踩法：

- 图片存放在书库之外（如 `~/Pictures`、其他分区），md 里用相对或绝对路径引用 → 一律 403；
- 与 BUG-001 联动：报告人当前书库是"上次恢复的旧目录"，而本次打开的 md 可能位于其他位置——若 md 本身不在书库内，其相对路径解析出的图片绝对路径也不在书库内 → 403；
- 另有无书库的独立文件场景：`root` 为 `null` 时同样 403。

### 候选 2：路径大小写不匹配 → 404（Linux 特有，macOS 默认大小写不敏感所以"看起来以前没事"）

Linux 文件系统区分大小写。若 md 中写 `Assets/Pic.PNG` 而磁盘上是 `assets/pic.png`，在 macOS（默认 APFS 大小写不敏感）可以正常渲染，在 Linux 上 readdir/readFile 直接 404。**用户肉眼核对路径时最容易漏掉的就是大小写。**

### 候选 3：md 中使用绝对路径 → 被错误拼接（平台无关，但 Linux 用户更常写绝对路径）

`preview.ts:176` 不判断 src 是否已是绝对路径，一律拼在文档目录后：`/home/u/docs` + `/` + `/home/u/pics/x.png` → `/home/u/docs/home/u/pics/x.png` → 404。凡是绝对路径引用的图片必然渲染失败（两平台皆然）。

### 候选 4：文件名含 `%` 等字符 → `decodeURIComponent` 抛异常，中断后续所有图片（平台无关，概率较低）

`preview.ts:175` 对 src 做 `decodeURIComponent`，若文件名含裸 `%`（如 `进度50%.png`）会抛 `URIError`，导致 **img 循环中断——该图之后的所有图片都不会被改写为 mdasset 地址**。表现为"一部分图不渲染"。

### 已排除项

- CSP 拦截：`img-src` 明确包含 `mdasset:`，排除；
- MIME 表缺项：常见格式齐全且 Chromium 对 `<img>` 有内容嗅探，基本排除；
- 应用内"插入图片"功能：写入的是相对路径 `assets/img-*.ext`，链路正常（但插入到**书库外**文档时同样会被候选 1 的 403 拦截）。

## 可诊断性缺陷（独立于根因，必须修）

**生产构建没有任何打开 DevTools 的入口**（全仓库无 `openDevTools` 调用），用户无法看到 403/404 网络错误；且 `<img>` 加载失败是静默空白。这使本类问题对普通用户完全黑盒，也是本单难以远程定位的直接原因。

## 待补充信息（报告人可后续追加，用于裁决候选根因）

- [ ] 图片与 md 文档是否都在**左侧文件栏显示的那个目录**（当前书库）之内？
- [ ] md 中图片 src 写的是相对路径还是绝对路径？原文片段可贴一行（如 `![x](assets/pic.png)`）；
- [ ] 路径各段的大小写与磁盘实际文件名是否完全一致（逐字符核对）；
- [ ] 文件名是否含空格、`%`、`#`、`?`、中文等特殊字符；
- [ ] 是"所有图片都不渲染"还是"部分不渲染"（部分→候选 4 权重上升）；
- [ ] 该文档在 macOS 版（如有）打开时图片是否正常（正常→候选 2 权重上升）；
- [ ] Linux 发行版与文件系统类型（ext4/btrfs/…）。

## 修复建议（按优先级）

1. **图片加载失败可见化**：给预览区 `<img>` 挂 `onerror`，显示占位框与原因（403=不在书库内 / 404=文件不存在），这是把黑盒变可诊断的关键一步；
2. **支持绝对路径 src**：`preview.ts` 中用 `path.isAbsolute`（或 `/` 开头判断）跳过 baseDir 拼接；
3. **书库外图片策略决策**：维持 403（安全优先）则需在插入/渲染时给出明确提示；或允许"文档所在目录"作为第二信任根（比整个文件系统仍收窄）；
4. **`decodeURIComponent` 包裹 try/catch**，单张图片处理失败不应中断整个循环；
5. **大小写容错**（可选）：404 时对父目录做一次大小写不敏感匹配并在提示中告知正确写法；
6. **受限诊断入口**：菜单增加"复制诊断信息"（当前书库根、文档路径、失败图片的解析结果与响应码），替代不可用的 DevTools。

## 修复与验收（2026-10-15）

- 本地图片路径统一在主进程解析，支持相对路径、库内父目录、绝对路径、`file://` 和 `mdasset://`；绝对路径不再错误拼接。中文、空格、百分号以及编码的 `#?` 只解码一次；存在的未编码 `#?` 文件名优先匹配，不存在时按 URL 查询/片段后缀解析。
- Markdown 图片语法单独允许本地文件地址，普通链接的校验不变。原始图片地址保存在当前渲染的私有映射中，隔离插件不能通过伪造图片属性获得新文件访问。
- 图片可位于当前书库或成功打开的 Markdown 文档所在文件夹。主进程检查实际路径、普通文件、图片类型和读取权限，拒绝越界和逃逸符号链接；关闭或切换书库撤销旧授权。库外文档按 BUG-001 的统一入口切换书库，解决旧书库误挡其图片的场景。
- 每张图片独立处理；缺失、越界、权限和损坏均显示包含 alt、原因与路径的占位。浏览器加载错误会再次查询本地诊断，文件可读但解码失败时提示损坏或格式问题，不猜测 403/404。错误地址不影响后续图片，旧加载事件不能修改新文档。
- Chromium 实际解码验收覆盖相对、父目录、绝对、file URL、中文空格、裸百分号、编码与未编码 `#?`；并验证错误图片后仍可显示正常图片、越界/缺失/损坏占位及延迟旧图隔离。另有权限、协议错误、目录边界、符号链接与撤销授权的真实文件系统回归。
